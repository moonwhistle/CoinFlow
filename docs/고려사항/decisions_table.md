# ID 생성 전략 및 시간 모델 설계 결정

본 문서는 암호화폐 실시간 차트 데이터 파이프라인 MVP 구축 과정에서 선택한 **ID 생성 전략**과 **시간 모델**에 대한 설계 의도와 근거를 기록한다.
단기적인 구현 단순성과 장기적인 확장 가능성 사이의 트레이드오프를 명확히 하기 위함이다.

---

## 1. ID 생성 전략 (GenerationType.IDENTITY)

### 결정 사항
- 모든 엔티티의 기본 키 생성 전략으로 `GenerationType.IDENTITY`를 사용한다.

### 선택 이유
- MVP 단계에서는 **구현 단순성과 명확성**을 최우선으로 한다.
- IDENTITY 전략은 데이터베이스에 키 생성을 위임하는 방식으로, 초기 개발 및 디버깅 비용이 낮다.
- 현재 시스템에서는 대량 배치 인서트가 상시 발생하지 않으며, `MissingTickLog` 역시 정상 상황에서는 소량 로그만 누적되는 구조다.(예상)

### 인지하고 있는 제약
- IDENTITY 전략은 Hibernate/JDBC 레벨에서 배치 인서트 최적화가 제한될 수 있다.
- 장애 상황에서 `MissingTickLog`가 대량으로 누적될 경우, 성능 병목이 발생할 수 있다.

### 향후 전환 계획
- 운영 환경에서 대량 적재로 인한 병목이 실제로 관측될 경우, `SEQUENCE + Hibernate pooled optimizer` 전략으로 전환을 고려한다.

---

## 2. 시간 모델 설계 (UTC 기준 + LocalDateTime)

### 결정 사항
- 모든 시간 값은 **UTC 기준**으로 저장한다.
- 엔티티에서는 표현 타입으로 `LocalDateTime`을 사용한다.

### 적용 대상
- `tickTime`, `startTime`, `endTime`
    - 시장(거래소) 기준 시간 (UTC)
- `detectedAt`
    - 시스템 이벤트 발생 시간 (UTC)

### 선택 이유
- MVP 단계에서는 **표현의 단순성과 가독성**을 우선한다.
- `LocalDateTime`은 도메인 로직과 조회 시 직관적인 표현을 제공한다.
- 시간의 기준을 **UTC로 명시적으로 고정**함으로써, 타임존 혼동을 방지한다.

### 인지하고 있는 제약
- `LocalDateTime` 자체는 타임존 정보를 포함하지 않는다.
- 서버가 다중화되거나 분산 환경으로 확장될 경우, 애플리케이션과 DB 간 시계 불일치 문제가 발생할 수 있다.

### 향후 전환 계획
- 분산 환경 또는 타임존 관련 이슈가 실제로 발생할 경우,`Instant` 또는 `OffsetDateTime` 기반 모델로 전환한다.

---

## 요약

- 본 설계는 MVP 단계에서의 **단순성·명확성·개발 속도**를 우선한 결정이다.
- 성능 및 분산 환경 이슈는 이미 인지하고 있으며, 운영 단계에서 무리 없이 전환 가능하다.
